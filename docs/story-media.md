# Картинки, GIF и видео в историях

В Angular-редакторе выберите «Добавить фото, GIF или видео», перетащите файл в поле истории или вставьте изображение из буфера обмена. Файл вставляется в текущую позицию курсора. Можно добавить подпись, включить предпросмотр и убрать вложение до отправки. В ленте показывается первое вложение, на странице истории — все; видео запускается пользователем.

## Публикация и форматы

История публикуется автоматически после **технической проверки файлов и проверки текста** в очереди RabbitMQ. Содержимое кадров, изображения, речь и звук автоматически не модерируются. Техническая проверка не является антивирусом. Неоднозначный текст, как и прежде, может потребовать оператора. Файл должен успешно обработаться до создания задания модерации.

| Формат | Ограничения | Обработка |
| --- | --- | --- |
| JPEG / PNG | 10 MiB, 20 MP | Декодирование, удаление исходных метаданных, повторное кодирование до 2048 px; прозрачность PNG сохраняется |
| GIF | 15 MiB, 60 с, 300 кадров, 40 млн пикселей суммарно | Повторное кодирование анимации до 1280 px, удаление исходных метаданных |
| MP4 | 50 MiB, 120 с, 8.3 MP; H.264, опционально AAC | Проверка потоков и длительности, remux без перекодирования, faststart |
| WebM | 50 MiB, 120 с, 8.3 MP; VP8/VP9/AV1, опционально Opus/Vorbis | Проверка потоков и длительности, remux без перекодирования |

До 8 вставок на историю; квота аккаунта — 200 файлов / 500 MiB обработанных данных. SVG, HTML, произвольные внешние URL и неподдерживаемые кодеки не принимаются. Для H.264 требуется совместимость с браузером пользователя; автоматического HLS/адаптивного стриминга и перекодирования видео пока нет. Для GIF/видео используются FFmpeg/ffprobe, устанавливаемые Dockerfile только в domain runtime; отдельный контейнер не нужен. Подпроцессы имеют ограничения времени, потоков и допустимых протоколов. Domain обрабатывает одну загрузку одновременно; превышение текущей ёмкости возвращает 429.

## API

Все приватные операции требуют пользовательский Bearer JWT; запись — `api.write`, чтение — `api.read`.

1. `POST /api/v1/story-media`, `Content-Type: application/octet-stream`, тело — байты файла. Ответ `201` содержит `id`, `kind`, `contentType`, `sizeBytes`, размеры и длительность. MIME и расширение клиента не определяют допустимость содержимого.
2. В `body` истории вставьте `![Подпись](attachment:UUID)`. Создайте/обновите историю обычным POST/PUT с `If-Match` для правки. Допустимы только собственные успешно обработанные файлы. Ответ истории содержит `attachments` без S3-ключей и данных владельца.
3. `GET /api/v1/story-media/{id}/access` возвращает `{media, url, expiresAt}`. Относительный `url` действителен пять минут и подходит для `img`/`video`.
4. `GET`/`HEAD` по этому URL работают без OAuth-токена в адресе. Поддерживаются одиночные, открытые и suffix Range: `206` / `416`. URL содержит короткоживущую подпись доступа, поэтому его тоже нельзя публиковать или логировать. Каждый запрос дополнительно проверяет актуальный доступ к файлу. Angular получает новую ссылку при ошибке загрузки и сохраняет позицию видео.
5. `DELETE /api/v1/story-media/{id}` — удалить свой неиспользуемый файл, `204`. Пока файл связан с рабочей или опубликованной версией, возвращается `409`. Сначала опубликуйте правку без вложения либо удалите историю.

Полный контракт: [openapi.json](openapi.json). Для проверки через реальный gateway после запуска: `python3 scripts/test-story-media.py` (локальные OAuth/Mailpit и RabbitMQ обязательны).

## Хранение, версии и доступ

Байты хранятся в существующем **приватном S3/Garage bucket**, PostgreSQL хранит метаданные, состояние загрузки и связи с версиями историй. Имена файлов пользователя не становятся S3-ключами. Бинарные файлы не попадают в RabbitMQ и PostgreSQL. Истории/вложения резервируются транзакционно с блокировками; нельзя привязать файл другого автора или удалить его одновременно с привязкой.

Файлы неизменяемы. Для новой картинки создаётся новый объект. Пока правка проходит модерацию, читатели получают вложения прежней одобренной версии; вложения новой версии видит автор. При одобрении обновляются текст и доступ к вложениям. После удаления ссылки из обеих актуальных версий читатель теряет доступ даже по ранее подписанному URL. Удаление истории удаляет связи; файлы затем забирает сборщик.

Журнал загрузки позволяет собрать объект после сбоя между S3 и БД. Неиспользуемые готовые файлы очищаются через 24 часа, незавершённые — через час. Удалённые вручную — ближайшим проходом worker. Сетевые операции очистки выполняются вне транзакции, с lease и повторными попытками. Резервные копии должны включать PostgreSQL **и** S3; учтите префикс `stories/` в IAM/lifecycle-политиках существующего bucket. Сборщик не должен соревноваться с независимой lifecycle-политикой, удаляющей ещё используемые объекты.

## Обновление и production

Обновите оба репозитория. Из backend:

```sh
git pull
docker compose up -d --build --wait --wait-timeout 600
```

Flyway V8 добавит таблицы, сохранив существующие истории. Версия политики — `basic-v2`; pending-задания переводятся на неё и отправляются повторно. Producer/domain и moderation-service нужно обновлять вместе: старые решения не одобряют новую политику. Frontend Docker необходимо пересобрать, dev server — перезапустить. Оба Nginx содержат отдельный streaming-маршрут с лимитом 50 MiB и таймаутом 120 секунд; у внешнего reverse proxy должны быть совместимые лимиты.

Production требует **новый секрет** `secrets/story-media-signing-key` (случайная строка минимум 32 байта), смонтированный только в domain как `STORY_MEDIA_SIGNING_KEY`. Новая установка создаёт его через `provision-secrets.py`. Для существующего каталога добавьте только недостающий файл, не пересоздавая остальные секреты:

```sh
python3 -c 'import os,secrets; fd=os.open("secrets/story-media-signing-key",os.O_WRONLY|os.O_CREAT|os.O_EXCL,0o600); os.write(fd,secrets.token_urlsafe(48).encode()); os.close(fd)'
sudo chown 999:999 secrets/story-media-signing-key
sudo chmod 0400 secrets/story-media-signing-key
```

Dev-ключ запрещён в профиле `prod`. Все реплики domain должны иметь один ключ; его ротация делает старые пятиминутные ссылки недействительными. Production использует HTTPS. Query подписанных media URL исключён из access log обоих Nginx; аналогично настройте внешний ingress, APM и CDN. Не кешируйте приватные файлы в общем CDN: ответы `private, no-store`.

По выбранному режиму `MODERATION_MEDIA_REVIEW_REQUIRED=false`. При необходимости ручного просмотра **каждой** истории с медиа задайте `true` и пересоздайте moderation-service. Меняется digest правил в аудите; уже обработанные версии автоматически не перепроверяются. Оператор с доверенным доступом к БД может создать приватный HTML-предпросмотр:

```sh
python3 scripts/preview-story-media.py STORY_UUID --revision 2
# Production: добавьте --origin https://api.example.com --key-file secrets/story-media-signing-key
python3 scripts/moderate-story.py STORY_UUID --revision 2 --approve --operator admin --reason "Проверено вручную"
```

Предпросмотр хранится в `.credentials/` с правами 0600 и содержит пятиминутные ссылки; не отправляйте HTML другим людям. Для полноценной визуальной модерации дальше нужен отдельный этап анализа/ручного решения до публикации; текущий флаг позволяет включить такой ручной барьер.

## Изолированные проверки

Без OAuth, UI, RabbitMQ, Qdrant и модели рекомендаций:

```sh
docker compose -p plot-twist-media-test -f compose.media-test.yaml build
docker compose -p plot-twist-media-test -f compose.media-test.yaml run --rm media-tests
docker compose -p plot-twist-media-test -f compose.media-test.yaml down -v
```

Этот проект имеет собственные PostgreSQL, Garage и Maven cache, не публикует порты и не использует пользовательские данные. Проверяет реальные PNG/GIF/MP4/WebM, S3-загрузку и HTTP Range, подделку/истечение подписи, владение, рабочие/опубликованные версии, удаление и очистку. Решения модерации в media-тестах подаются прямо в DecisionStore; настоящий RabbitMQ проверяется отдельно через `compose.moderation-test.yaml`. CI запускает оба набора отдельно и smoke через весь gateway.
