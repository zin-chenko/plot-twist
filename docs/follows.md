# Подписки на авторов

В профиле другого пользователя есть кнопка «Подписаться», после нажатия — «Отписаться». Счётчики показывают число подписчиков и подписок просматриваемого аккаунта. На своей странице кнопки подписки на себя нет. В ленте появилась вкладка **«Подписки»** (`/feed?view=following`): опубликованные истории выбранных авторов, включая более ранние, от новых к старым. Фильтр сохраняется после F5.

Подписка односторонняя и не требует подтверждения; взаимные подписки разрешены. На одного автора от одного аккаунта может существовать одна связь. Повторный запрос не добавляет подписчиков повторно и не переключает состояние. При ошибке интерфейс сохраняет прежнее состояние и предлагает повторить операцию. Следующий запрос устанавливает то же желаемое состояние.

## HTTP API

Нужен проверенный пользовательский JWT. Actor ID берётся из `account_id`/`sub`, не из тела запроса или параметров URL.

- `PUT /api/v1/profiles/{account}/follow`, scope `api.write`, без тела — подписаться. Неизвестный автор — `404`; на себя — `400`.
- `DELETE /api/v1/profiles/{account}/follow`, scope `api.write` — отписаться. Отсутствующая связь также даёт успешный ответ. На себя — `400`.
- Оба метода возвращают `200`, `Cache-Control: no-store` и `{following, followersCount, followingCount}`. Счётчики относятся к **целевому** аккаунту; `following` — связь текущего читателя с этим аккаунтом.
- `GET /api/v1/profiles/{account}`, scope `api.read`, теперь дополнительно возвращает эти три поля. Состояние персонально для читателя и не предназначено для общего кеша.
- `GET /api/v1/stories/following?limit=10&cursor=…`, scope `api.read` — `{items, nextCursor}`, limit 1–20. Лента определяется подписками JWT-пользователя; чужой account ID не меняет выборку.

Лента показывает только одобренные снимки текста/версии/вложений. Новые ожидающие/отклонённые истории не видны; при проверке правки остаётся прежняя публикация. Отписка убирает автора из последующих чтений ленты, сохраняя его истории, ваши оценки и комментарии. Пагинация по `(created_at,id)` читает текущие связи; для новых публикаций и новых подписок выше уже пройденного курсора обновите ленту.

Незаполненный аккаунт, участвующий в подписках, отображается как «Читатель» без персональных полей. Удаление **данных профиля** не удаляет аккаунт и его подписки: ник/описание/фото очищаются, связи сохраняются. Удаление аккаунта в auth-service в этом проекте пока не реализовано; при его добавлении нужно отдельно удалять входящие и исходящие связи по identity event.

## Хранение и масштабирование

Flyway V9 добавляет `user_follows` в БД domain. Составной primary key `(follower_id, following_id)` запрещает дубликаты, CHECK запрещает self-follow, обратный индекс обслуживает подписчиков. FK в таблицу профилей нет: профиль может быть не заполнен или удалён, identity принадлежит auth-service.

Изменение связи — короткая транзакция с advisory lock на **пару** аккаунтов; PUT/DELETE одной связи упорядочены между репликами. Популярный автор не блокирует все подписки на себя одним общим lock. Счётчики читаются из реальных связей, поэтому повторные запросы не накапливают ошибочные инкременты. Никакие тексты и файлы по подписчикам не размножаются.

Пока используется fan-out on read: PostgreSQL читает одобренные истории с `EXISTS` по подпискам, курсором и индексом историй автора. Это соответствует текущему размеру проекта. Для миллионов связей/высокого RPS нужно измерить планы и p95: далее возможны асинхронные агрегаты счётчиков, кеш и гибридная материализация ленты с outbox/Kafka. Текущая реализация не обещает проверенную на таком масштабе пропускную способность. Отдельный сервис или очередь для самой операции подписки сейчас не нужны.

## Обновление и тесты

Сначала обновите backend, чтобы применить V9 и новые API, затем frontend. Секреты не добавляются.

```sh
# В каталоге backend
git pull
docker compose up -d --build --no-deps --wait domain-service api-service gateway
# В каталоге frontend
git pull
docker compose up -d --build --wait
# Для dev frontend вместо Docker перезапустите npm start.
```

Без полного стека:

```sh
docker compose -p plot-twist-profile-test -f compose.profile-test.yaml run --rm --build profile-tests
docker compose -p plot-twist-profile-test -f compose.profile-test.yaml down -v
```

Изолированные проверки используют отдельную PostgreSQL и настоящие транзакции: повторные/взаимные подписки, одновременные PUT/DELETE, SQL-ограничения, scopes/identity, отсутствие чужих/неодобренных историй, курсор, оценки читателя и отписка. Брокер и S3 для них заменены заглушками. Браузерный UI-набор с HTTP fixtures проверяет кнопку, счётчики, отказ/повтор, собственный профиль, ленту подписок, её пустое состояние и F5. Проверка через весь развернутый стек остаётся отдельным этапом.
