# Подписки на авторов

В профиле другого пользователя есть кнопка «Подписаться», после нажатия — «Отписаться». Счётчики показывают число подписчиков и подписок просматриваемого аккаунта. На своей странице кнопки подписки на себя нет. В ленте появилась вкладка **«Подписки»** (`/feed?view=following`): опубликованные истории выбранных авторов, включая более ранние, от новых к старым. Фильтр сохраняется после F5.

Подписка односторонняя и не требует подтверждения; взаимные подписки разрешены. На одного автора от одного аккаунта может существовать одна связь. Повторный запрос не добавляет подписчиков повторно и не переключает состояние. При ошибке интерфейс сохраняет прежнее состояние и предлагает повторить операцию. Следующий запрос устанавливает то же желаемое состояние.

## HTTP API

Нужен проверенный пользовательский JWT. Actor ID берётся из `account_id`/`sub`, не из тела запроса или параметров URL.

- `PUT /api/v1/profiles/{account}/follow`, scope `api.write`, без тела — подписаться. Неизвестный автор — `404`; на себя — `400`.
- `DELETE /api/v1/profiles/{account}/follow`, scope `api.write` — отписаться. Отсутствующая связь также даёт успешный ответ. На себя — `400`.
- Оба метода возвращают `200`, `Cache-Control: no-store` и `{following, followersCount, followingCount}`. Счётчики относятся к **целевому** аккаунту; `following` — связь текущего читателя с этим аккаунтом.
- `GET /api/v1/profiles/{account}`, scope `api.read`, теперь дополнительно возвращает эти три поля. Состояние персонально для читателя и не предназначено для общего кеша.
- `GET /api/v1/stories/following?limit=10&cursor=…`, scope `api.read` — `{items, nextCursor}`, limit 1–20. Лента определяется подписками JWT-пользователя; чужой account ID не меняет выборку.

Лента показывает только одобренные снимки текста/версии/вложений. Новые ожидающие/отклонённые истории не видны; при проверке правки остаётся прежняя публикация. Отписка убирает автора из последующих чтений ленты, сохраняя его истории, ваши оценки и комментарии. Пагинация по `(created_at,id)` читает текущие связи; для новых публикаций и новых подписок выше уже пройденного курсора обновите ленту.

Незаполненный аккаунт, участвующий в подписках, отображается как «Читатель» без персональных полей. Удаление **данных профиля** не удаляет аккаунт и его подписки: ник/описание/фото очищаются, связи сохраняются. Удаление аккаунта в auth-service в этом проекте пока не реализовано; при его добавлении нужно отдельно удалять входящие и исходящие связи по identity event.

## Хранение и масштабирование

Flyway V9 добавляет `user_follows` в БД domain. Составной primary key `(follower_id, following_id)` запрещает дубликаты, CHECK запрещает self-follow, обратный индекс обслуживает подписчиков. FK в таблицу профилей нет: профиль может быть не заполнен или удалён, identity принадлежит auth-service.

Изменение связи — короткая транзакция с advisory lock на **пару** аккаунтов; PUT/DELETE одной связи упорядочены между репликами. Популярный автор не блокирует все подписки на себя одним общим lock. Счётчики читаются из реальных связей, поэтому повторные запросы не накапливают ошибочные инкременты. Никакие тексты и файлы по подписчикам не размножаются.

Пока используется fan-out on read: PostgreSQL читает одобренные истории с `EXISTS` по подпискам, курсором и индексом историй автора. Это соответствует текущему размеру проекта. Для миллионов связей/высокого RPS нужно измерить планы и p95: далее возможны асинхронные агрегаты счётчиков, кеш и гибридная материализация ленты с outbox/Kafka. Текущая реализация не обещает проверенную на таком масштабе пропускную способность. Отдельный сервис или очередь для самой операции подписки сейчас не нужны.

## Обновление и тесты

Сначала обновите backend, чтобы применить V9 и новые API, затем frontend. Секреты не добавляются.

```sh
# В каталоге backend
git pull
docker compose up -d --build --no-deps --wait domain-service api-service gateway
# В каталоге frontend
git pull
docker compose up -d --build --wait
# Для dev frontend вместо Docker перезапустите npm start.
```

Без полного стека:

```sh
docker compose -p plot-twist-profile-test -f compose.profile-test.yaml run --rm --build profile-tests
docker compose -p plot-twist-profile-test -f compose.profile-test.yaml down -v
```

Изолированные проверки используют отдельную PostgreSQL и настоящие транзакции: повторные/взаимные подписки, одновременные PUT/DELETE, SQL-ограничения, scopes/identity, отсутствие чужих/неодобренных историй, курсор, оценки читателя и отписка. Брокер и S3 для них заменены заглушками. Браузерный UI-набор с HTTP fixtures проверяет кнопку, счётчики, отказ/повтор, собственный профиль, ленту подписок, её пустое состояние и F5. Проверка через весь развернутый стек остаётся отдельным этапом.

## Списки подписчиков и подписок

Нажмите на число «Подписчики» или «Подписки» в своём или чужом профиле. Откроется модальное окно со списком с аватарами, никами и переходами к профилям. Для следующих записей есть «Показать ещё пользователей». Метка «Вы подписаны» относится к текущему читателю; «Это вы» отмечает его собственную запись. Окно закрывается кнопкой «Закрыть», Escape или кликом по затемнённому фону; фокус возвращается к счётчику. Поиск по нику работает по всей выбранной группе, включая ещё не загруженные страницы.

API: `GET /api/v1/profiles/{account}/followers` и `GET /api/v1/profiles/{account}/following`, scope `api.read`. Ответ `{items, nextCursor}`; элемент содержит только `{accountId, displayName, photoSha256, following}`. Размер страницы — 1–20, по умолчанию 20. Курсор ограничен 240 символами, связан с профилем и направлением списка; чужой курсор даёт 400. Сортировка — `(created_at, member_account_id)` по убыванию; Flyway V10 добавляет индексы для обоих направлений. Собственный пустой список доступен и без заполненных личных данных. Остальные неизвестные профили дают 404. История реальных дат подписки и личные поля не возвращаются.

Списки читают текущие связи. Если подписки меняются во время просмотра, обновите список для новых записей выше пройденного курсора. Интерфейс отменяет применение устаревших ответов при смене профиля/направления. Байты аватаров загружаются через существующий защищённый API.

## Суммарные лайки и просмотры

`PublicProfile` дополнен `totalLikes` и `totalViews`; числа показаны в своём и чужом профиле:

- `totalLikes` — число текущих положительных оценок всех существующих одобренных историй автора. Дизлайки не вычитаются, снятие лайка или смена на дизлайк уменьшает число. Отдельный пользователь может оценить несколько историй, каждая оценка учитывается.
- `totalViews` — уникальные пары **читатель + история**. Считается успешный сигнал открытия полной истории через существующий `POST /stories/{id}/reading`, а не показ карточки в ленте. Повторный F5, дочитывание и новая редакция той же истории не добавляют просмотр от того же аккаунта. Собственные открытия автора исключены. Учитываются принятые сервером сигналы; это не система выявления ботов или измерения анонимных просмотров.

Обе суммы относятся к опубликованным историям. Проверяемая правка сохраняет показатели прежней публикации; новые неодобренные истории не учитываются. Удаление истории убирает её лайки и просмотры из сумм.

Flyway V10 создаёт `story_views` с ключом `(story_id, account_id)`. Запись выполняется в той же короткой транзакции, что и сигнал чтения, после проверки опубликованной истории и с `ON CONFLICT DO NOTHING`. Параллельные открытия не накручивают число. Срабатывает и при выключенных рекомендациях; чистка 90-дневных `story_read_signals` не удаляет `story_views`. При удалении истории её записи удаляются по FK.

Миграция переносит доступную историю из оставшихся сигналов чтения, исключая автора и неопубликованные истории. **Данные, уже удалённые 90-дневной очисткой до обновления, восстановить невозможно**. Новые просмотры сохраняются независимо от этой очистки. При очень больших объёмах просмотров понадобятся измерения p95 и отдельные агрегаты для быстрого чтения сумм; сейчас источником служат реальные записи PostgreSQL.

Для этого обновления сначала пересоберите backend до V10, затем frontend. Команды обновления и изолированного тестирования выше остаются теми же. Тесты дополнены переходом V9 → V10 с сохранённой историей, конкурентными чтениями, очисткой рекомендаций, изменением оценок, удалением истории и пагинацией списков.

## Модальное окно и поиск

Все четыре показателя профиля оформлены одинаковыми карточками в один ряд; интерактивными остаются только «Подписчики» и «Подписки». Списки открываются в нативном `dialog` с затемнением фона, ограничением фокуса внутри окна и полем поиска. Фоновая страница не прокручивается, поиск отправляется после паузы 250 мс; устаревшие ответы не заменяют новый результат.

GET-методы списков поддерживают `q`: до 80 символов после удаления внешних пробелов, без NUL. Поиск — регистронезависимая подстрока публичного ника, применяется в PostgreSQL до пагинации. `%`, `_`, `+` и другие символы не превращаются в команды или шаблон поиска. При изменении запроса следующая страница сбрасывается; курсор связан с профилем, направлением и поиском. Старые курсоры без поиска поддерживаются. Личные поля в поиск не входят.

Для этого изменения достаточно обновить приложения backend и frontend; новых миграций и секретов нет. API-gateway и HTTP-адаптер сохраняют кириллицу и специальные символы без повторного URL-кодирования. Проверки покрывают поиск по всему списку, экранирование, курсоры, закрытие окна клавишей/мышью и возврат фокуса.
