# Графики Prometheus и Grafana

В локальном Docker Compose мониторинг запускается вместе с приложением. Конфигурация datasource и дашборд добавляются автоматически; ручной импорт JSON не нужен.

```sh
docker compose up -d --build --wait --wait-timeout 180
```

- **Grafana:** http://localhost:3000/d/plot-twist-overview — `Plot Twist · Backend Overview`.
- **Локальный вход:** пользователь `admin`, пароль `plot-twist-local`.
- **Prometheus:** http://localhost:9090 — запросы к метрикам; `/targets` показывает реплики и статус опроса.

Адреса работают и с `127.0.0.1`. Для другого порта задайте `GRAFANA_PORT` или `PROMETHEUS_PORT` в локальном `.env`; пароль первоначального admin — `GRAFANA_ADMIN_PASSWORD`. Эти настройки не являются учётной записью пользователя приложения.

Первую учётную запись Grafana создаёт при инициализации `grafana-data`. Затем пароль меняется через настройки аккаунта Grafana: изменение env не сбрасывает пароль существующего пользователя. После входа домашняя страница открывает готовый дашборд; он также доступен в папке **Dashboards → Plot Twist**.

## Что показывают панели

Дашборд содержит 29 панелей, включая:

- HTTP RPS по сервисам и отдельным репликам API;
- p50, p95 и p99 на основе HTTP bucket-гистограмм;
- долю 5xx и отдельные коды 4xx/5xx;
- CPU Java-процессов, heap/non-heap, GC-паузы и потоки платформы;
- активные/максимальные соединения Hikari, ожидающие запросы и таймауты пула auth/domain;
- очереди писем и отложенной очистки фото;
- доступность scrape каждой реплики и время с запуска процесса.

Сверху доступны фильтры **Сервис** и **Реплика**, диапазон времени и автообновление каждые 15 секунд. Prometheus обновляет DNS discovery каждые 10 секунд, поэтому после масштабирования API новые реплики появляются без ручного списка адресов.

Общий `env_file` — `monitoring/java-metrics.env` — включает HTTP-гистограммы всех Java-сервисов через `SPRING_APPLICATION_JSON` и добавляет статическую метку replica. Настройки наследуются и production Compose. Изменение этого файла требует пересоздания Java-контейнеров, без пересборки JAR. Для запуска вне Compose передайте те же management properties в конфигурацию Spring.

HTTP-графики исключают `/actuator/**`. Сумма RPS Java-сервисов не равна внешнему ingress RPS: один запрос пользователя проходит API и domain и может учитываться в обоих. Аналогично, HTTP p95 — время обработки отдельного сервиса, а не полная задержка пользователя. Реплика отображается по статическому Docker hostname; запросы не получают меток email, токена или account ID.

`up=1` означает успешное получение метрик, а не полную readiness-проверку БД/S3. Hikari показывает пулы приложения; это не мониторинг самого PostgreSQL. CPU — Java-процесс, а не вся машина. Для метрик ОС, PostgreSQL и Nginx потребуются отдельные exporters. Экспорт логов и трасс в Grafana в этот набор не входит; текстовые логи доступны через `docker compose logs`.

## Если график пустой

После первого запуска подождите **30–60 секунд**: для `rate()` нужны минимум два опроса. Затем зарегистрируйтесь, откройте профиль, сохраните данные или загрузите фото. Без запросов RPS равен 0, а p95/p99 могут не вычисляться — тестовые значения не подставляются.

При фильтре `api-service` графики БД и очередей пусты: этих компонентов у API нет. Пустые очереди auth/domain показывают 0. Если данных нет вообще, проверьте:

```sh
docker compose ps
docker compose logs --tail=100 prometheus grafana
python3 scripts/test-monitoring.py
```

На http://localhost:9090/targets по умолчанию должны быть UP **четыре** target: две реплики API, auth и domain. Проверка `test-monitoring.py` подтверждает provisioning, реальные метрики и RPS/p95; она делает несколько безопасных анонимных запросов с ожидаемым 401, которые будут видны на графиках. При масштабировании задайте `EXPECTED_API_INSTANCES` для ожидаемого количества реплик.

Панели проверяются в Prometheus по реальным метрикам, дашборд расположен в `monitoring/grafana/dashboards/backend-overview.json`. Он управляется кодом и недоступен для изменения поверх provisioning; для своих экспериментов сохраните копию в Grafana.

## Хранение и доступ

Оба интерфейса публикуются только на `127.0.0.1`. Grafana требует вход; регистрация и анонимный доступ отключены. Prometheus опрашивает Java по приватной сети `services`; Grafana подключена к отдельной сети `monitoring` с Prometheus, без подключения к сети Java-сервисов. Публичный gateway не открывает actuator. Одноразовый `monitoring-config` копирует версионируемые YAML/JSON в отдельные конфигурационные тома и устанавливает права чтения. Он не имеет сети и не касается томов с данными. Runtime-контейнеры читают конфиги в режиме read-only; это также устраняет зависимость от прав bind-mount файлов на Linux. При изменении конфигов пересоздайте init-контейнер: `docker compose up --force-recreate monitoring-config`, затем `docker compose restart prometheus grafana`.

Метрики хранятся в `prometheus-data`: retention 7 дней или 512 MB старых TSDB-блоков, что наступит раньше. WAL и индексы требуют дополнительного места; это не жёсткая дисковая квота. `grafana-data` сохраняет аккаунты и пользовательские настройки. Обычный `docker compose down` сохраняет оба тома. Образы закреплены digest, контейнеры имеют read-only rootfs, лимиты памяти и ограниченные Docker-логи.

## Production

В `compose.prod.yaml` мониторинг включается явно профилем `monitoring`. Локальный пароль удаляется при merge; Grafana получает первоначальный admin password через secret-файл `secrets/grafana-admin-password`. Новое выполнение `scripts/provision-secrets.py` создаёт его случайным вместе с остальными секретами. Для ранее подготовленного каталога создайте этот отдельный файл самостоятельно с помощью менеджера секретов, не перезаписывая БД/ключ подписи.

На production Linux-хосте файл должен читаться UID **472** (Grafana), например `chown 472:0 secrets/grafana-admin-password` и `chmod 0400 secrets/grafana-admin-password`. Для прочих секретов сохраняются требования из [production runbook](production.md).

```sh
docker compose -p plot-twist-prod --profile monitoring --env-file .env.production \
  -f compose.yaml -f compose.prod.yaml up -d --build --wait --wait-timeout 180
```

Порты остаются loopback-only. С удалённого компьютера используйте SSH-туннель:

```sh
ssh -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 user@server
```

После этого открываются те же localhost-адреса. Публичные TLS/SSO и оповещения требуют отдельной настройки выбранной площадки; этот Compose не выполняет внешнее production-развёртывание.

Панели рекомендаций показывают общую очередь индексации (max, не sum по репликам), dead jobs, обработку/ошибки и режимы новых снимков выдачи. `fallback` не означает готовую смысловую модель. [Диагностика ML](recommendations.md).
