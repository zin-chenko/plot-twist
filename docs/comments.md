# Комментарии: лайки, сортировка и ответы

На странице истории у каждого активного комментария/ответа есть **лайк** и **Ответить**. Один аккаунт ставит один лайк; повторное нажатие снимает его. Своим комментариям ставить лайки разрешено. Дизлайков комментариев нет. Лайк меняет счётчик на месте, не переставляя карточку во время просмотра.

Сортировка основного списка:

- **Сначала новые** — createdAt/id по убыванию, по умолчанию.
- **Сначала старые** — createdAt/id по возрастанию.
- **Популярные** — количество лайков по убыванию; при равенстве сначала новые.

Смена сортировки или обновление списка начинает новую пагинацию. Популярный порядок фиксируется на 15 минут, чтобы новые/снятые лайки не дублировали и не пропускали карточки между страницами. Счётчики и myLiked остаются актуальными. Для популярной сортировки берутся до 500 лучших корневых комментариев; полный список доступен в режимах по дате. Новые/старые используют keyset без OFFSET. Курсоры привязаны к аккаунту, истории, сортировке и корню ветки; просроченный/чужой/несовместимый курсор получает 400.

## Ветки

Ответы раскрываются кнопкой **Ответы · N**, загружаются отдельными страницами и идут хронологически. Можно ответить и на исходный комментарий, и на ответ другого пользователя. Внутри ветки ответы показаны на одном уровне с подписью «В ответ: имя», чтобы длинные обсуждения оставались читаемыми на телефоне. `parentId` указывает непосредственного собеседника, `rootId` — исходный комментарий. Для корня оба поля null. На API нельзя переместить существующий комментарий или подставить другой rootId: сервер вычисляет его сам и проверяет принадлежность одной истории.

Редактирование/удаление доступны только автору конкретного комментария; автор истории не получает прав на чужие ответы. При редактировании используется прежний `If-Match` и проверка версии. Лайки версию текста не меняют. При 412 UI сохраняет черновик и предлагает загрузить свежую версию.

Удаление листового комментария без дочерних записей физическое: следующий GET даёт 404. Если есть ответы, сервер очищает текст/лайки и сохраняет `deleted=true` с пустым body: UI показывает **Комментарий удалён**, сохраняя чужую ветку. Удалённый комментарий нельзя редактировать, лайкать или использовать как новый непосредственный parent. Ответить на живой ответ внутри такой ветки по-прежнему можно. Полностью опустевшая удалённая корневая ветка скрывается из списка. Исторические заглушки не учитываются в счётчиках.

`Story.commentCount` — число всех живых комментариев, включая ответы, без заглушек. `replyCount` у корня — все живые ответы в его ветке; у ответа — его непосредственные живые дети. `likes` — текущий счётчик, `myLiked` — состояние только JWT-пользователя. Обновлённые DTO также включают `parentId`, `rootId`, `replyToAuthorName`, `deleted`. Текст отображается через Angular-интерполяцию, без HTML.

## API

Базовый путь: `/api/v1/stories/{id}/comments`. Все операции требуют подтверждённого пользовательского JWT. GET — `api.read`, изменения — `api.write`; account/author ID в теле не принимается. История должна иметь одобренную опубликованную версию. Ответы `Cache-Control: no-store`.

| Метод | Путь | Тело/назначение |
|---|---|---|
| GET | `/comments?sort=newest&limit=10&cursor=…` | Только корни; sort=newest/oldest/popular, limit 1–20 |
| POST | `/comments` | `{body}` для корня; `{body,parentId}` для ответа; 201 |
| GET | `/comments/{commentId}` | Актуальный DTO и ETag; для заглушки body пустой |
| PUT | `/comments/{commentId}` | `{body}`, свой If-Match; 200/412/428 |
| DELETE | `/comments/{commentId}` | Свой комментарий; 204, ответы не удаляются |
| PUT | `/comments/{commentId}/like` | Без тела; идемпотентно поставить лайк, возвращает DTO |
| DELETE | `/comments/{commentId}/like` | Без тела; идемпотентно снять свой лайк, возвращает DTO |
| GET | `/comments/{rootId}/replies?limit=10&cursor=…` | Все ответы данной ветки, старые сначала, отдельный cursor |

В таблице пути сокращены относительно `/api/v1/stories/{id}`. Полный контракт — [OpenAPI 1.12.0](openapi.json). Старые запросы `POST {body}` и `GET /comments` продолжают работать; ранее выданный курсор после обновления нужно получить заново. Лимит текста — 2000 UTF-16 единиц, пустой текст и управляющие символы (кроме переноса/табуляции) отклоняются.

## Хранение и конкурентность

Комментарии остаются в domain-service, в функции story. HTTP выделен в `CommentController`, сценарии — `CommentService`, SQL — `JdbcCommentRepository` через порт `CommentRepository`. Транспортный api-service передаёт пути/параметры/JWT, не имеет доступа к БД. Нового сервиса или брокера для этого не требуется.

Flyway **V13** добавляет связи веток, soft-delete marker, counter, `comment_likes` и краткоживущие таблицы popular ranking. Существующие комментарии становятся корневыми без изменения текста/авторства. Составные внешние ключи (story_id,parent/root_id) запрещают ответы в другую историю. UNIQUE(comment_id,account_id) обеспечивает один лайк; INSERT ON CONFLICT / DELETE и PostgreSQL-триггер меняют counter только при фактическом изменении лайка. Это не меняет текстовую version.

Изменения берут shared lock опубликованной истории, затем блокируют сначала корень, затем целевой ответ — единый порядок защищает от гонок ответа/удаления и deadlock между операциями ветки. Изменения разных веток не блокируют друг друга, удаление истории каскадно удаляет её комментарии/лайки/снимки. Popular batches ограничены 500 строками, выдача и очистка имеют индексы. Истёкшие batches удаляются фоновыми ограниченными порциями; снимок привязан к viewer/story и не позволяет чужой доступ. Это инженерные ограничения первой версии, а не измерение предельной пропускной способности.

## Обновление

В backend, ветка `feature/spring-boot-docker-compose`:

```sh
git pull --ff-only
docker compose up -d --build --no-deps --wait domain-service api-service gateway
```

Существующие зависимости стека должны работать. V13 применяется автоматически, volumes удалять не нужно. **api-service обновляется вместе с domain-service**, включая обе реплики, иначе новые маршруты лайков/ответов будут возвращать 404. Gateway пересобирается также для актуального `/openapi.json`.

Затем обновите frontend `plot-twist-web`, ветка main: `git pull --ff-only` и перезапуск/обновление `npm start`; для Docker пересоберите web. Новых секретов и дополнительных контейнеров нет.

## Проверки без полного стека

```sh
docker compose -p plot-twist-profile-test -f compose.profile-test.yaml run --rm --build profile-tests
docker compose -p plot-twist-profile-test -f compose.profile-test.yaml down -v
```

Этот отдельный тестовый проект использует PostgreSQL и включает `COMMENTS_INTEGRATION=true`: конкурентные/idempotent лайки, cursor/sort/owner binding, popular snapshot, ответы на ответы, cross-story FK, tombstones, авторство/версии/scope, удаление истории, гонка создания ответа с удалением родителя. Модель, S3, RabbitMQ и реальный OAuth не требуются. API gateway проверен отдельными MVC-тестами. Флаг добавлен в уже существующий изолированный CI job профилей/снимков.

В frontend `PLAYWRIGHT_PORT=4300 npm test` (PowerShell: сначала `$env:PLAYWRIGHT_PORT="4300"`). HTTP/OAuth fixtures проверяют лайки/ошибки, сортировку, пагинацию, ответ на ответ, редактирование/конфликт черновика, сохранение уже загруженных ответов после отправки, удаление родителя с чужим ответом и мобильную ширину. Это проверка UI-контракта; полный deployment с настоящими аккаунтами — отдельная проверка при запуске.
